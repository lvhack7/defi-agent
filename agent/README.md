# Agent backend

See the root README. `npm run server` serves the built dashboard/API on loopback; `npm start` runs the CLI. Use one at a time. Root `.env.local` is loaded by either script.

Managed ZooWork SDK 0.14.0 lifecycle/session methods are retained. Tool implementations live in `tools.mts`; the runtime reconciles these owned tool declarations while preserving unrelated ones. Dashboard chat sends the connected wallet (or entered watch address) and selected network on every turn. The backend validates that context, includes it in a single documented `user.message` input, and fills missing wallet/network tool fields. Live checks found `system.message` returns HTTP 502 on this deployment, even in an ordered batch, while persisting the note; that event type is avoided here. The UI displays only the user's original question. Mismatched wallet/network inputs are rejected; legacy Sepolia tools cannot operate under a different selected network. Context and a stable pending user-message key are retained for recovery after a gateway failure or restart. CLI financial tools still require an explicit network and wallet. The model can validate and prepare proposals but cannot sign, submit, or enable real-money execution.

Connect a wallet, choose a network, and ask: “How much ETH do I have, and what is it worth?” No address is needed in the message. ETH USD value comes from the ETH asset valuation, not the total portfolio value. Sepolia shows test USDC value instead. Disconnecting clears the active address; wallet context is not authentication or signing permission.

Users choose the token direction and swap amount in chat. There is no standing allocation ratio. Rebalance proposals use a target only when explicitly chosen by the user; portfolio analysis and direct swaps do not require one. Earlier conversation targets must not be treated as application policy.

The backend warms the managed runtime at startup. Chat streams show the current stage and elapsed time; sanitized terminal timing logs separate startup, delivery, tool reads, and agent response. Ordinary SDK HTTP requests have a 30-second timeout, response streams have a 90-second deadline, and browser chat requests have a 120-second deadline. A timeout can leave a remote run active; recovery retains its context, user-message delivery key, and processed cursor. `/api/agent-status` reports local readiness and sanitized initialization failures. Errors expose HTTP status or DNS/authentication categories without forwarding raw URLs, headers, or API response bodies. Portfolio market and balance reads run concurrently while keeping native/token balances pinned to the same block.

Keys stay on the backend. The UI relays only origin-checked local requests and sanitized events/text. Run this as a local single-operator service, not a public multi-user deployment.
